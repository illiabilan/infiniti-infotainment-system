# CL-7: Емулятор як клієнт Кора (роль sim)

Джерело: рішення власника Q1 під час CL-1/CL-2. Залежить від: CL-1, CL-2. Блокує нічого.

## Контекст

Після CL-1/CL-2 єдиний `VehicleState` у Корі гарантовано лише для dashboard, climate і cluster. Емулятор (`emulator/src/main.cpp`) і далі створює власний CAN-бекенд і власний `VehicleState`, бо:
- кадри двигуна, швидкості й передачі кодуються з його полів (`broadcast*()`),
- він слухає CAN, щоб його 100-мс heartbeat (`broadcastAll`) не перезаписував значення клімату, які виставили клієнти через Кор.

Мета: емулятор не відкриває CAN і не створює `VehicleState`. Він працює як звичайний клієнт Кора: `VehicleModel` плюс `CoreClient`, команди йдуть через `vehicle_set`. Дзеркало емулятора наздоганяє стан Кора, тому перезапису немає.

Область: `core/app/`, `core/protocol/`, `core/client/`, `emulator/`, `docs/design/clients.md`.

## Рішення

- Нова роль `sim` у `hello`. Для неї білий список груп `vehicle_set` розширюється групами, які клієнти зараз надсилати не можуть (Engine, SpeedBrake, Gear, Tpms, Telltales, OccupantsAlerts, ModeTheme). Для ролей `dash`, `cluster`, `climate` білий список не змінюється (`ALLOWED_CLIENT_GROUPS` у `core/app/CoreServer.h`).
- Роль `sim` приймається лише тоді, коли Кор працює на mock CAN. На SocketCAN `hello` з роллю `sim` відхиляється помилкою з новим кодом (наприклад `forbidden_role`). Причина: інакше будь-який локальний процес змусить Кор слати кадри двигуна на реальну шину авто.
- `CanBackendFactory` повідомляє, який бекенд обрано, щоб Кор міг застосувати обмеження.

## Ризики

- R1. Керування передачею й швидкістю через Кор на реальній шині. Закрито обмеженням на mock CAN, потребує тесту.
- R2. Затримка: кожна зміна демо-режиму (крок 33 мс) тепер іде через WebSocket і назад. Перевірити, що демо не гальмує.
- R3. Емулятор перестає бути незалежним джерелом CAN. Для перевірки Кора без емулятора лишається `core_test send` та сторонні відправники кадрів.
