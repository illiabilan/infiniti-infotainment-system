# CL-6: Розбиття ClusterController під ліміт 700 рядків

Джерело: рішення власника Q3 під час CL-1/CL-2. Правило: `AGENTS.md`, розділ Core Code Principles, пункт 1.

Залежить від: немає. Блокує нічого. Робити окремо від CL-4, щоб не змішувати рефакторинг з новою функціональністю кластера.

## Контекст

`cluster/src/ClusterController.cpp` має 1516 рядків, `cluster/src/ClusterController.h` має 655. Ліміт файлу 700 рядків. Клас об'єднує кілька відповідальностей (стан гейджів, телтейли, поїздка, медіа, налаштування користувача, демо-режим без VehicleState), що порушує Single Responsibility.

У CL-1 у цьому файлі виконано лише механічне перейменування типу (`VehicleState` на `VehicleModel`, 70 доданих і 70 видалених рядків). Кількість рядків не змінилась.

Область: `cluster/src/ClusterController.{h,cpp}` і нові файли в `cluster/src/`.

## АС

- [ ] `ClusterController.cpp` і `ClusterController.h` та всі нові файли не перевищують 700 рядків.
- [ ] Поведінка кластера не змінена. Перевірка: чек-лист 10 пунктів з `docs/traces/README.md`, або порівняння скріншотів до і після.
- [ ] Публічний API для QML (властивості, сигнали, `Q_INVOKABLE`) не змінюється, QML-файли не редагуються.
- [ ] Розбиття за відповідальностями, без дублювання логіки (DRY). Кожен новий клас має одну причину для зміни.
- [ ] Кластер не відкриває CAN (grep `SocketCanBackend\|MockCanBackend` у `cluster/` порожній).
- [ ] Збірка Debug проходить без нових попереджень.
